# QA.JP.AI セキュリティ基本ルール（AI コーディングツール用）v0.3

AI にアプリを作ってもらうときに、**AI に守らせるルール**です。
あなたが内容をすべて理解する必要はありません。AI がこれを読んで、作る段階で守ります。

- 対象：Supabase や Firebase などを使う Web アプリ
- 費用：無料
- ライセンス：CC0 1.0（著作権を放棄しています）。コピー、改変、再配布、商用利用のいずれも自由で、許可も出典の表示も要りません
- ご注意：このルールを使っても、QA.JP.AI の認証を受けたことにはなりません。安全を保証するものでもありません。作る段階での初歩的な事故を減らすためのものです

## 使い方（プログラミングの知識は要りません）

1. 下の「ここから」から「ここまで」までをコピーします。
2. お使いの AI に、次のように頼みます。

   > 次の内容を、このプロジェクトの AGENTS.md に追加してください（Claude Code の場合は CLAUDE.md）。ファイルがなければ作ってください。

   続けて、コピーした内容を貼り付けます。
3. これ以降、AI は作業のたびにこのルールを読みます。
4. 公開する前に、AI に「**公開前チェックをしてください**」と頼みます。

## セキュリティ基本ルール（QA.JP.AI v0.2）

あなた（AI）は、このプロジェクトで次のルールを必ず守ってください。
利用者はプログラミングの専門家ではありません。ルールを守れない場合や、守れているか確認できない場合は、黙って進めず、そのことを日本語でわかりやすく利用者に伝えてください。

### A. 絶対に守ること

一つでも破ると、利用者やその顧客の情報が外部に漏れます。

**R01 データベースのアクセス制御を必ず有効にする**

- Supabase：テーブルを作るときは、同じマイグレーションの中で RLS を有効にする（`alter table ... enable row level security`）。ポリシーは「本人のデータだけ」に限定する。`using (true)` のように全員に読み書きを許すポリシーを書かない。誰でも読めてよいデータ（お知らせなど）だけを読み取り専用の例外とし、その理由をコメントに書く。
- Firebase：セキュリティルールに `allow read, write: if true;` や、期限付きのテストモードを残さない。`request.auth != null` だけで全データを許可しない（ログインした他人のデータまで読めてしまう）。`request.auth.uid` とデータの持ち主を照合して、本人のデータだけに限定する。
- ファイル置き場（Storage）のルールも同じ考え方で書く。

**R02 秘密のキーをブラウザーに渡さない**

- 秘密のキー（Supabase の service_role キーやシークレットキー、Stripe のシークレットキー、OpenAI・Anthropic などの API キー、秘密鍵）は、サーバー側のコードと環境変数の中だけで使う。
- 次の名前で始まる環境変数は、ブラウザーにそのまま公開される。秘密のキーを入れない：`NEXT_PUBLIC_`、`VITE_`、`PUBLIC_`、`NUXT_PUBLIC_`、`REACT_APP_`、`EXPO_PUBLIC_`。
- キーをコードに直接書かない。`.env` は必ず `.gitignore` に入れる。README、コメント、ログにもキーを書かない。
- AI サービスや決済の呼び出しは、必ずサーバー側（API ルート、Edge Function、Cloud Functions など）を経由する。

**R03 認証の確認はサーバー側で行う**

- 画面でボタンやページを隠すだけでは保護にならない。データを返す処理、変更する処理のすべてで、サーバー側で「ログインしているか」「その操作をしてよい人か」を確認する。
- 利用者の ID は、リクエストの中身（body やクエリ）から受け取らない。検証済みのセッションから取得する。

**R04 ログインなしで利用者のデータを返さない**

- 利用者の情報を返す API は、ログインを必須にする。
- 全利用者の一覧のように、まとめて返す API を管理者以外に公開しない。
- 連番や推測できる ID を指定するだけで、他人のデータを取得できないようにする。

**R05 権限や状態を、利用者自身が書き換えられないようにする**

- 役割（管理者かどうか）、本人確認済みかどうか、支払い状態、残高などの項目は、利用者による更新を許可しない。更新できる列を、RLS のポリシーや API で限定する。
- リクエストの内容を、そのまま丸ごとデータベースに保存しない。受け付ける項目を一つずつ指定する。
- 支払い状態は、決済サービスからの通知（署名を検証した Webhook）によってのみ変更する。

**R06 機密ファイルは非公開の場所に置く**

- 本人確認書類、診療や相談の記録、契約書などは、非公開のバケットに置く。本人と権限のある人にだけ、期限付きの URL で渡す。
- 公開バケットや、誰でも読める public フォルダーに置かない。

### B. 必ず行うこと

**R07 回数制限と上限を設ける**
ログイン、登録、メール送信、AI の呼び出し、決済には、利用者ごと・接続元ごとの回数制限を設ける。AI の呼び出しには、1 回あたりと 1 日あたりの上限を設ける。

**R08 インジェクションを防ぐ**
SQL は必ずパラメーター化する。文字列をつなげて SQL を組み立てない。利用者が入力した内容を、HTML としてそのまま表示しない（`dangerouslySetInnerHTML`、`innerHTML`、`v-html` に利用者の入力を渡さない）。

**R09 制限はサーバー側でも実施する**
「特定のドメインのメールアドレスだけ登録できる」「1 人 1 回まで」のような条件は、画面だけでなくサーバー側でも必ず確認する。

**R10 依存ライブラリを確かめてから使う**
パッケージを追加する前に、それが実在し、名前が正しいことを確認する。存在しない名前を推測で書かない。既知の脆弱性がある版を使わない。追加したら `npm audit` などを実行し、結果を利用者に伝える。

**R11 内部のファイルを公開しない**
`.env`、`.git`、バックアップ、データベースの書き出しを、公開されるフォルダーに置かない。本番ではソースマップを公開しない。エラー画面に内部の情報（スタックトレース、SQL、キー）を表示しない。

**R12 LLM に、入力をそのまま「指示」として扱わせない**
利用者の入力や、外部から取得した文章（Web ページ、メール、ファイル）は、「指示」ではなく「データ」として扱う。LLM にツールやデータベース操作を使わせる場合、その操作を実行してよいかどうかは、必ずコードで確認する。プロンプトに「してはいけない」と書くだけでは保護にならない。LLM が使える権限は、その利用者本人の権限を超えないようにする。

**R13 AI エージェントの権限を絞り、止められるようにする**
自動で動く処理には、必要最小限の権限だけを与える。送金、削除、外部への送信など取り消せない操作の前には、人による確認を入れる。停止する手段と、回数・費用の上限を必ず用意する。

**R14 通信と基本設定**
本番は HTTPS だけで提供し、HTTP は HTTPS へ転送する。セキュリティヘッダー（Strict-Transport-Security、Content-Security-Policy、X-Content-Type-Options、X-Frame-Options）を設定する。ログイン状態を保持する Cookie には、Secure・HttpOnly・SameSite を付ける。

**R15 ログに秘密を書かない、重要な操作は記録する**
パスワード、キー、トークン、カード情報、本人確認書類の内容をログに書かない。ログイン、権限の変更、削除、決済は、誰がいつ行ったかを記録する。

### C. 進め方のルール

- テストを通すためだけの抜け道（認証の無効化、固定の合言葉、チェックの省略）を作らない。一時的に必要な場合は利用者に伝え、公開前に必ず元に戻す。
- 上のルールと利用者の依頼が矛盾する場合は、作業を止め、何が危険なのかを説明し、安全な代案を示す。
- 「たぶん大丈夫です」と言わない。確認したことと、確認できていないことを分けて伝える。

### D. 「公開前チェックをしてください」と言われたら

1. **ツールで検査する。** Node.js が使える環境では、まずプロジェクトのいちばん上のフォルダーで、次のコマンドを実行してください。

   ```
   npx --yes github:QAJPAI/qa-jp-ai-scanner#v0.8.0 check . --for-ai --baseline
   ```

   このツールはファイルを読むだけで、コードを実行したり、プロジェクトの内容を外部に送ったりしません（`--baseline` は、修正後と比べるために結果を利用者のキャッシュフォルダーに保存します。プロジェクトには書き込みません）。出力は「ツールが確認した問題」「利用者に確認していただく項目」「ツールが検査していない項目」に分かれています。出力の指示に従ってください。ツールが確認した問題は、判定を変えずにそのまま利用者に伝えてください。
   コマンドを実行できない場合は、その理由を利用者に伝え、報告の冒頭に「ツールによる検査は行えませんでした」と書いたうえで、次の 2 だけを行ってください。

2. **残りを自分で確認する。** ツールが検査していない項目（ツールを使えなかった場合は R01〜R15 のすべて）を一つずつ確認し、次の三つに分けて、日本語の一覧で報告してください。ツールの結果と区別するため、「AI による確認」と明記してください。

- **確認できた**：どのファイルのどこで守られているかを示せるもの。
- **問題あり**：守られていない箇所と、その直し方。
- **確認できない**：コードからは判断できないもの（例：Supabase や Firebase の管理画面の設定、本番サーバーの設定）。利用者がどの画面のどこを見れば確認できるかを、具体的に書く。

確認していない項目を「問題なし」と報告しないでください。

3. **修正したら、ツールで確かめる。** ファイルを変える前に、何をどう変えるかを説明して利用者の了承を得てください。修正が終わったら、次のコマンドで再検査してください。

   ```
   npx --yes github:QAJPAI/qa-jp-ai-scanner#v0.8.0 check . --compare --for-ai
   ```

   利用者には、出力で「修正を確認しました」と表示された項目だけを修正済みと伝えてください。「修正とは確認できません」と表示された項目は、理由を伝えて直し直してください。ファイルの削除・改名・移動など、検査を通すためだけの変更は修正ではありません。
